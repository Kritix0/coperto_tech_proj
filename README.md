# Стоп-лист кухни — Coperto

Панель менеджера зала: меню смены, фильтры, постановка позиций в стоп-лист и снятие
со стопа с оптимистичными обновлениями. Тестовое задание (Middle Frontend).

**Стек:** Next.js 15 (App Router), TypeScript (strict), Tailwind CSS v4, TanStack Query v5,
Zustand, React Hook Form + Zod, Framer Motion.

---

## Запуск

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Бэкенд имитируется route
handler'ами Next.js — отдельный сервер поднимать не нужно.

Дополнительно:

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # ESLint
npm run test        # Vitest (юнит-тест оптимистики)
npm run build       # прод-сборка
```

Экран рассчитан на десктоп (ориентир 1280px). Мобильной вёрстки нет, но на узком
экране макет не разъезжается.

## Как разложены слои

```
app/
  layout.tsx                     # шрифт (Inter), провайдеры, Toaster
  page.tsx                       # серверный компонент: читает searchParams
  providers.tsx                  # QueryClientProvider (клиентский)
  api/menu-items/route.ts        # GET списка (задержка 700мс)
  api/menu-items/[id]/stop/route.ts    # POST постановки в стоп
  api/menu-items/[id]/resume/route.ts  # POST снятия со стопа

features/stop-list/
  api/menu-api.ts                # транспорт: единственное место с fetch
  model/queries.ts               # ключи кэша + queryOptions
  model/use-menu-items.ts        # чтение списка + клиентская фильтрация
  model/use-stop-item.ts         # хук мутаций (связка React ↔ оптимистика)
  model/optimistic.ts            # чистая логика оптимистики (покрыта тестом)
  model/filters-core.ts          # чистый парсер фильтров (клиент + сервер)
  model/filters.ts               # хук чтения/записи фильтров в URL
  model/schema.ts                # Zod-схемы (клиент + сервер)
  model/ui-store.ts              # Zustand: панель, тосты, «сохраняется»
  ui/StopListView.tsx            # оркестратор: связывает данные и UI
  ui/StopListTable.tsx           # презентация таблицы, без запросов
  ui/StopReasonPanel.tsx         # форма постановки/редактирования
  ui/Filters.tsx                 # селекты фильтров

shared/
  ui/                            # Button, Select, Input, Badge, Field, Toaster…
  domain.ts                      # подписи доменных значений
  format.ts                      # форматирование срока/времени

server/
  menu-store.ts                  # сид + in-memory хранилище
  sim.ts                         # имитация задержки и нестабильности

types/menu.ts                    # доменные типы
```

Направление зависимостей одно: `ui → model → api → server`. UI-компоненты не знают
о транспорте; они получают данные и колбэки от `StopListView`. Транспорт (`menu-api.ts`)
— единственный модуль, где есть `fetch` и знание про URL и формат ответа.

## Граница сервер / клиент

- **Серверные компоненты:** `app/page.tsx` (читает `searchParams`, считает начальные
  фильтры и SSR-подпись) и route handler'ы в `app/api/**`.
- **Клиентские компоненты:** всё интерактивное — `providers.tsx`, `StopListView` и его
  дети, хуки состояния, стор. Помечены `'use client'`.
- Чистая логика, которая нужна обеим сторонам (`filters-core.ts`, `schema.ts`), вынесена
  в модули **без** `'use client'`, чтобы её можно было звать и на сервере, и на клиенте.
  (Именно поэтому парсер фильтров живёт отдельно от хука `useMenuFilters`.)

## Архитектурные решения и почему

1. **Один список в кэше, фильтрация на клиенте.** GET отдаёт всё меню под единственным
   ключом `['menu-items','list']`. Фильтры цеха/статуса — производное состояние поверх
   этого списка, а не отдельные запросы. Так оптимистика остаётся атомарной: мутация
   правит единственный источник правды, нет гонок между разными закэшированными
   списками, а переключение фильтра происходит мгновенно, без рефетча. Это сознательное
   отступление от примера в задании (`menuKeys.list(filtersKey)`): при небольшом меню
   смены выгода в простоте и предсказуемости оптимистики важнее серверной фильтрации.

2. **URL — источник правды для фильтров.** Состояние читается из `searchParams` и
   пишется через `router.push`. Переживает перезагрузку и корректно работает с кнопкой
   «назад» (каждое изменение фильтра — запись в историю).

3. **Оптимистика вынесена из React.** `optimistic.ts` — чистые фабрики опций мутаций
   (`onMutate` снимает снапшот и патчит кэш, `onError` откатывает, `onSettled`
   инвалидирует). Хук `use-stop-item.ts` только прокидывает туда `QueryClient` и
   побочки (тосты, метка «сохраняется»). Благодаря этому логику отката удалось покрыть
   юнит-тестом без рендера компонентов.

4. **Zustand только для UI-состояния.** В сторе живут открытая панель, тосты и множество
   «сохраняемых» id. Серверные данные в сторе не дублируются — они в кэше Query.

5. **Одна Zod-схема на клиент и сервер.** `stopItemPayloadSchema` валидирует форму на
   клиенте (через `zodResolver`) и тело запроса в route handler'е. Правила срока стопа
   (в будущем, ≤24ч, шаг 15 минут) описаны один раз в `validateUntil`.

## Правила стоп-листа (проверяются на клиенте и на сервере)

- Причина обязательна, только одно из четырёх значений `StopReason`.
- Срок: либо «до конца смены» (`until: null`), либо конкретное время — строго в будущем,
  не позже 24 часов, шаг 15 минут.
- При остатке `0` кнопка «Вернуть в продажу» заблокирована с подсказкой.
- Повторная постановка уже застопленной позиции открывает форму в режиме
  редактирования причины и срока.

## Допущения (спорные места)

- **Остаток 0 → авто-стоп.** Позиция, приходящая доступной с остатком 0, автоматически
  уходит в стоп по причине «закончились продукты» (инвариант в `menu-store.ts`, на
  чтении). Уже застопленную по другой причине позицию не трогаем.
- **Причину `out_of_stock` при остатке >0 не запрещаем.** Менеджер может знать то, чего
  нет в остатке (брак, бронь), поэтому оставляем ручной override, а не блокируем выбор.
- **Панель постановки закрывается по ответу сервера, а не мгновенно.** Строка меняет
  статус оптимистично сразу, но панель держит спиннер на кнопке до ответа: успех —
  закрытие, ошибка — панель остаётся для повтора (совмещает «статус меняется сразу» и
  «лоадер на кнопке» из ТЗ).

## Про in-memory состояние на Vercel

Хранилище (`server/menu-store.ts`) живёт в памяти процесса. Локально (`next dev`)
изменения сохраняются до перезапуска сервера. На Vercel serverless каждый холодный старт
инстанса поднимает свежий сид, поэтому изменения могут «сбрасываться» между запросами —
это ожидаемое поведение мока, а не баг. Для реального продукта сюда встало бы постоянное
хранилище (БД).

## Что бы доделал при наличии времени

- Тесты на хук `useMenuFilters` (синхронизация с URL и кнопкой «назад») и на форму
  панели (валидация onBlur/submit).
- Гонки мутаций по одной позиции: сейчас `onSettled` инвалидирует список; при частых
  кликах стоило бы отменять устаревшие мутации/дебаунсить.
- Вынести токены дизайна (цвета, отступы) в более формальную тему и добавить состояние
  фокуса/ховера по всем интерактивным элементам единообразно.
- Пагинация/виртуализация, если меню смены вырастет до сотен позиций (сейчас сознательно
  не нужно по условию).
- Более богатый a11y-аудит (focus trap внутри панели, возврат фокуса на триггер).

## Что реализовано из бонусов

- Одна Zod-схема на клиент и route handler.
- Аккуратные анимации на Framer Motion (появление панели, смена статуса, тосты),
